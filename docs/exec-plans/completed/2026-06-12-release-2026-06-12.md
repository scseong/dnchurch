## 롤백 계획

마이그레이션은 Supabase 자동 롤백 대상이 아니다. 종류별로 롤백 방식을 다르게 정한다.

- **보안 마이그레이션 2건은 forward-only — 코드를 되돌려도 롤백하지 않는다.**
  - `20260611000000_profiles_rls_lockdown.sql`: 롤백하면 anon에게 profiles 전 컬럼 권한이 다시 열려 PII 조회와 본인 role을 admin으로 바꾸는 권한 탈취가 되살아난다.
  - `20260611000001_harden_bulletin_rpc.sql`: 롤백하면 anon이 로그인 없이 `create_bulletin`·`update_bulletin`을 호출해 주보 생성·수정·타 주보 이미지 삭제가 되살아난다.
  - 함수 자체에 장애가 나면 롤백 대신 접근을 끊는다: `REVOKE EXECUTE ON FUNCTION create_bulletin(TEXT, DATE, UUID, JSONB) FROM authenticated;` (update_bulletin도 동일), 다음 배포에서 수정.
- **스키마/RPC 추가 마이그레이션(sermon 테이블, bulletin_rpc 등)은 additive — 코드 롤백 시 그대로 둔다.** 신규 테이블·함수는 기존 흐름에 영향을 주지 않으므로 남겨도 무해하다. 데이터 정리가 필요하면 수동 `DROP`으로 처리.
- **코드 롤백**: main을 직전 릴리스 커밋으로 되돌려 재배포. DB는 위 롤백 방식을 따른다.
- **롤백 후 확인**: 기존 주보·인증 흐름 정상 동작, profiles anon 직접 조회 차단 유지.

## 의사결정 로그

- **D1 — 보안 마이그레이션을 forward-only로 둔다**
  - 문제: 릴리스를 되돌릴 때 16개 마이그레이션을 일괄 롤백하면 profiles RLS 잠금과 bulletin RPC 가드가 함께 풀려, 이번에 막은 anon 권한 탈취·PII 유출 구멍이 되살아난다.
  - 해결: 보안 마이그레이션 2건(`profiles_rls_lockdown`·`harden_bulletin_rpc`)은 코드 롤백과 분리해 DB에 유지한다. 코드를 직전 릴리스로 되돌려도 이 둘은 남긴다 — 롤백 이득(코드 회귀 복구)보다 취약점 재개방 손실이 크기 때문이다.
  - 결과: Codex CHANGE_REQUEST(harden_bulletin_rpc 롤백 경로 추상)가 닫혔다. 롤백 계획에 함수별 접근 차단 SQL과 forward-only 사유를 명시했다.
